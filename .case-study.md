# Case study: Agent telemetry

Coding agents on many VMs send their telemetry to one server, which stores it and shows it in Grafana.

This case study is for engineers who are evaluating, adopting or extending the stack. It explains the problem, the design decisions and their costs. Setup is in [README.md](README.md), procedures in [runbook.md](runbook.md), and the full detail in [REFERENCE.md](REFERENCE.md).

A few OpenTelemetry (OTel) terms are used throughout:
- OTel is the vendor-neutral standard for telemetry. It calls metrics, logs and traces *signals*, and OTLP (the OpenTelemetry Protocol) is the format they travel in.
- Every batch of telemetry carries *resource attributes* that describe the sender, such as `service.name` and `host.name`. Each data point, log record or span can also carry attributes of its own.
- The OpenTelemetry Collector is a relay that runs one *pipeline* per signal: *receivers* accept data, *processors* change it, and *exporters* send it on.

## At a glance

| | |
|---|---|
| **What** | A Docker Compose stack that receives metrics, logs and traces over OTLP, stores them, and shows them in eight provisioned Grafana dashboards: for each of **Claude Code** and **Grok Build**, a main dashboard, a work log, a flow timeline and a conversations view |
| **Agents covered** | Claude Code (built-in OTel SDK) and Grok Build (metrics and events), each with four dashboards. Any app that uses a standard OTel SDK can send data too, and it can be queried in Grafana's Explore and Drilldown. |

## The problem

AI coding agents run on many VMs, often headless (`claude -p`, a one-shot non-interactive run). The people who run them need answers to operational questions:

- How many sessions ran, on which VM, and for which user?
- What did they cost, and which models and users drove the cost?
- How many tokens were used, and how much of that came from the prompt cache?
- Which tools failed, which API calls errored, and how slow were the model calls?
- What did one specific long-running prompt do, step by step?

Claude Code already ships an OpenTelemetry SDK that emits this data:
- counters for sessions, cost, tokens, lines of code, commits and PRs;
- events for every prompt, API request and tool result;
- in beta, a trace per interaction, meaning one user prompt and everything the agent does to answer it.

Grok Build (`grok`), a terminal coding agent, emits similar metrics and events. What neither agent has is somewhere to send the data. The data becomes useful only once it leaves each VM, lands in one place, can still be attributed to the VM and user that produced it, and is counted correctly. That last part is harder than it sounds ([decision 1](#1-counting-correctly-with-delta-counters-and-short-lived-series)).

A self-hosted stack keeps all of this on one host that the team controls, and the agent VMs need to reach only that host. The cost is that the team itself runs storage, retention, upgrades, backups and access control for five services; the [limitations](#limitations-and-trade-offs) below are that cost. The repository doesn't record whether a hosted OTLP backend was considered.

## Goals and constraints

1. **One server, many agents.** A single host receives data from every agent VM over the network.
2. **Docker is the only runtime dependency.** Everything runs in containers, including certificate generation. The README even creates the secrets in `.env` with a throwaway `busybox` container that reads `/dev/urandom`. Data lives in named volumes, and configs are mounted read-only from the repo.
3. **Encrypted and authenticated at the edge.** Every published port uses TLS, OTLP needs a token, and the storage backends are never published. [Decision 2](#2-a-private-certificate-authority-inside-the-stack) and the limitations list what this leaves open.
4. **Correct numbers.** Totals in the dashboards must match what the agents did, even with short-lived sessions, idle agents and restarts.
5. **No data loss through ordinary backend trouble.** A backend restart, upgrade or brief outage must not drop data.
6. **Low-touch onboarding.** Connecting a VM takes one short block on the server (print the token, copy the CA) and one `nexus --config` run on the VM, which asks only for the endpoint, the token and the CA. Without nexus, it takes one block on the VM, run as root. Either way it changes no one's shell.
7. **Operable by someone who didn't build it.** Every routine task has a documented, copy-pasteable procedure.

## Architecture

Agents never talk to a backend directly. The collector sits in front of the backends, so that authentication, labelling ([decision 6](#6-a-second-agent-labelled-on-the-server-grok-build)), secret masking ([Also in the stack](#also-in-the-stack)), counter conversion ([decision 1](#1-counting-correctly-with-delta-counters-and-short-lived-series)) and the disk queue ([decision 3](#3-surviving-backend-outages-a-disk-queue-that-retries-indefinitely)) all happen in one place. From the network, the collector is the only way data enters the stack and Grafana is the only way to read it; Prometheus, Loki and Tempo are not published. On the host, `docker compose exec` also reaches the backends.

| Service | Role |
|---|---|
| `otel-collector` | Ingestion: authenticates, masks secret shapes in logs and traces, labels, converts delta counters to running totals, and queues to disk |
| `prometheus` | Metrics: OTLP from the collector, span metrics from Tempo (remote-write), and scrapes of every stack component's own metrics, including the collector's health metrics |
| `loki` | Logs and agent events |
| `tempo` | Traces, plus *span metrics* (request counts and latency histograms computed from spans) and a service graph derived from them |
| `grafana` | The UI (HTTPS), with provisioned datasources and dashboards |
| `init`, `certs` | One-shot containers without network access: volume ownership, a healthcheck probe binary, and the private CA |

Each signal has its own pipeline in the collector. Metrics are labelled and then converted to running totals. Logs have secret shapes masked, are labelled, and are then cleaned of duplicate attributes ([decision 4](#4-logs-few-index-labels-everything-else-as-structured-metadata)). Traces have secret shapes masked and otherwise pass straight through.

The collector forwards OTLP to each backend's native OTLP endpoint, so no backend-specific exporter is needed. Prometheus still maps OTLP onto its own model:
- `service.name` becomes `job`, and `service.instance.id` becomes `instance`.
- Five more resource attributes are copied onto every series: `service.version`, `deployment.environment`, `deployment.environment.name`, `host.name` and `os.type`.
- All other resource attributes exist only on `target_info`, one extra series per sending process that carries all of its resource attributes.
- Attributes on individual data points, such as Claude Code's `user_email`, `model` and `session_id`, always become labels.
- Names are rewritten in classic Prometheus style, so `claude_code.token.usage` becomes `claude_code_token_usage_tokens_total`.

A new attribute in `OTEL_RESOURCE_ATTRIBUTES` therefore can't be used as a label filter until it is added to `promote_resource_attributes` in `prometheus/prometheus.yml`. Until then it can be reached only by joining with `target_info`.

## Key design decisions

### 1. Counting correctly with delta counters and short-lived series

**Problem.** Claude Code exports **delta** counters: each export says how much a counter grew since the previous one (+3 tokens). Prometheus works with **cumulative** counters, which are running totals (1,203 tokens). OTel calls this choice a metric's *temporality*. On top of that, every Claude Code session has its own `session_id` label, so each session creates a new set of series that may export only once or twice. Plain PromQL handles this badly:
- A new series has no earlier sample, so `increase()` can't see its first value. A session that exports once counts as zero.
- `increase()` and `rate()` extrapolate to the edges of the time window. On short series this gives results such as "1.5 sessions" for one session.
- Agents send a series only when it changes, so after an idle period a bucket can hold a single sample, and measuring growth needs the value from before the bucket. The `anchored` modifier used below takes that value from the last earlier sample, but looks back no further than the *lookback delta* (5 minutes by default). With the default, the first increment after an idle gap of more than 5 minutes was lost.

The per-session series are kept on purpose. The docs say to leave `session_id` on metrics (Claude Code's default) because it keeps concurrent sessions apart, and the **Top Sessions by Cost** leaderboards depend on it.

**Decision.** Four settings and one query convention work together:
- The collector's `delta_to_cumulative` processor keeps a running total per series and forgets it after 30 minutes without data (`max_stale: 30m`). It tracks at most 200,000 series (`max_streams`). Agents need no temporality setting.
- Prometheus's experimental `created-timestamp-zero-ingestion` feature writes a `0` at each new OTLP series' start time, so the first export counts as an increase.
- Prometheus's experimental `promql-extended-range-selectors` feature enables the `anchored` range modifier. Every `increase()` in the dashboards and docs uses it, which removes the extrapolation.
- `--query.lookback-delta=31m` is deliberately one minute longer than the collector's 30-minute `max_stale`, so `anchored` still finds the previous value of a series that was idle for up to 30 minutes.
- The query convention: Grafana fills in `$__range` (the whole dashboard time range) and `$__interval` (the width of one graph bucket). Counter panels query either `increase(x[$__interval] anchored offset -$__interval)` (time series, and stat panels that add up their buckets) or `increase(x[$__range] anchored)` (leaderboards, pie charts, tables). The negative offset shifts each window forward, so each point covers exactly its own bucket. The Prometheus datasource's minimum interval (`timeInterval`) is 60 s, Claude Code's default metric export interval, and every counter panel sets a minimum bucket of 5 minutes or 1 hour, so buckets are never narrower than the data.

By construction, a panel's buckets cover its step-aligned range with no gaps, no overlap and no extrapolation, so the panel's total is the sum of its buckets.

**Trade-off.**
- The fix depends on two experimental Prometheus features.
- The running totals live in the collector's memory. A collector restart, or 30 minutes without data for a series, looks like a counter reset, and `increase()` handles that correctly. The same in-memory state is why only one collector can run: two collectors would each hold a partial total for the same series and send Prometheus conflicting values.
- Per-session series make the series count grow with the number of sessions rather than VMs. Prometheus keeps every session's series for up to 15 days, within its 1 GiB memory cap.
- The 31-minute lookback applies to every query, not only the dashboards'. An instant query returns a series' last value for up to 31 minutes after it stopped, so a VM that went quiet still looks current for that long. After that an instant query returns nothing, which is why the **Last seen** column in both dashboards' usage tables falls back to a subquery over the dashboard range.
- Because the first and last buckets are aligned to each panel's step, an hourly chart and a stat panel with 5-minute buckets can differ slightly at the edges of the range.

### 2. A private certificate authority inside the stack

**Problem.** OTLP and Grafana need TLS on networks that may have no public DNS and no ACME access (the protocol Let's Encrypt uses to issue certificates automatically). And with Docker as the only runtime dependency, there is no host `openssl` to rely on.

**Decision.** A one-shot `certs` container, built locally from `alpine:3.24.2` plus OpenSSL, runs a small private PKI (public-key infrastructure):
- **CA:** a private certificate authority (EC P-256, 10 years). Its key lives in the `tls-ca` volume, which no other service mounts.
- **Server certificate:** EC P-256, valid for 825 days, issued for the names and IPs (Subject Alternative Names) in `TLS_SANS`. One certificate serves ports 4317, 4318 and 3000. Two of the names, `DNS:localhost` (Grafana's healthcheck) and `DNS:grafana` (Prometheus's scrape of Grafana), are for the stack itself and must stay.
- **Re-issue:** whenever `certs` runs and `TLS_SANS` has changed or the certificate is within 30 days of expiry. `certs` runs on `docker compose up -d` for the whole stack, or for any service that depends on it. The CA stays the same, so agents never need a new CA after a renewal.
- **Key copies:** the private key is copied once for each consumer UID: `collector.key` for 10001 and `grafana.key` for 472, both mode `0400`. Each process reads its key as its own non-root user.
- **Reload:** the collector reloads its certificate every 24 h. Grafana loads a new certificate only on restart, so the runbook's renewal procedure restarts both.

**Trade-off.**
- Browsers and agents must trust a private CA.
- Nothing renews the certificate on a schedule. It is re-issued only when someone runs `up -d` within 30 days of expiry, which is why the runbook's health check prints the expiry date.
- `docker compose down -v` deletes the CA together with all data, and every agent then needs the new `ca.crt`. Backups contain the CA key (`tls-ca.tgz`) and `.env`, so they must be kept private.
- `.env` is state, not just configuration. It holds Grafana's two encryption keys, which must never change once Grafana stores secrets, and running README step 1 again regenerates every secret.
- TLS and the token protect the published ports. Inside the `otel` Docker network, traffic to and between the backends is plaintext and unauthenticated (only Prometheus's scrape of Grafana uses HTTPS). The collector writes to Prometheus and Loki over `http://` and to Tempo with `tls.insecure: true`, and Loki runs single-tenant. The trust boundary is the Docker network and the host.

### 3. Surviving backend outages: a disk queue that retries indefinitely

**Problem.** Backends restart for upgrades, config changes and backups. Agents retry only briefly and keep no local spool, so whatever the collector can't deliver is gone.

**Decision.** Each exporter queues to disk and retries until the data is delivered:
- **Durable:** the queue is fsync'd, so it survives host crashes, not only process restarts. Retries back off from 5 s to 30 s and never give up (`max_elapsed_time: 0s`). Queue size is the only bound.
- **Sized for the disk:** each queue holds 32 MiB of data, in a storage file capped at 256 MiB. The embedded key-value store (bbolt) can use about 8× the queued bytes for small requests. Across the three exporters, the worst case is 768 MiB of Docker disk.
- **Compaction:** queue files are compacted at every collector start. While the collector runs, a file that grew past 100 MiB is compacted once its contents fall back below 10 MiB.
- **Ordering:** the Prometheus exporter sends from a single worker, so samples arrive in time order. Loki and Tempo use four workers.

A disk queue only helps if the backends accept what it replays. Two Tempo defaults would quietly drop replayed data, so they are changed:
- The metrics generator accepts spans up to 15 minutes late into span metrics and the service graph (the default is 30 s). Spans replayed after a longer outage are still stored as traces, but they are missing from those metrics.
- `max_traces_per_user` is the number of traces Tempo holds in memory at once per tenant. Tempo refuses traces beyond it, and a replayed backlog delivers many traces at once, so the limit is raised from 10,000 to 100,000. Memory stays bounded by the 250 MB limit on the live store, Tempo's in-memory store of recent traces.

Separately, Prometheus accepts samples up to 30 minutes out of order, for agents with clock skew or retrying exporters.

The backup procedure relies on the queue: it stops the backends, and the collector holds incoming data until they are back.

**Trade-off.**
- Every queue write waits for fsync.
- Prometheus gets no parallel export.
- The queue doesn't cover requests the collector rejects with 401, for example from VMs still on a rotated token ([decision 5](#5-onboarding-through-managed-settings)).
- Even with the queue, data is lost in four cases. The collector's own metrics show three of them, and the Claude Code dashboard's **Collector health** row graphs them:

| Data is lost when… | Signal |
|---|---|
| The queue is full | `otelcol_exporter_enqueue_failed_*` |
| A backend permanently rejects a record, e.g. HTTP 400 | `otelcol_exporter_send_failed_*`, plus the collector logs |
| The collector hits its memory limit and refuses incoming data | `otelcol_receiver_refused_*` |
| The collector itself is down | Only the `otel-collector` scrape target going down |

A restore also discards whatever was queued, because backups don't include the queue volume.

### 4. Logs: few index labels, everything else as structured metadata

**Problem.** Loki keeps one *stream*, with its own index entry and storage chunks, for each unique combination of index labels. Loki's built-in OTLP defaults turn a list of resource attributes into index labels. That list includes high-cardinality ones such as `service.instance.id`, which would multiply the number of streams. Meanwhile, per-event fields such as `session_id`, `user.email` and (with beta tracing) `trace_id` must stay searchable. Some events also carry large payloads.

**Decision.**
- Loki indexes only five low-cardinality resource attributes (`ignore_defaults: true`): `service.name`, `service.namespace`, `deployment.environment`, `deployment.environment.name` and `host.name`. Every other attribute is *structured metadata*: it is stored with each line, isn't indexed, and can be filtered after `|` in LogQL.
- The structured-metadata limit is raised from 64 KB to 256 KB, and the internal gRPC message limits from 4 MB to 100 MB. With the defaults, Loki answers HTTP 400 to records whose metadata exceeds 64 KB, and drops them. Queries over records with large metadata fail with "trying to send message larger than max".
- A collector `transform` processor deletes the `host.name` and `deployment.environment.name` log attributes when they equal the resource value. Claude Code copies `OTEL_RESOURCE_ATTRIBUTES` onto every log record, and Loki would otherwise store each copy a second time.

**Trade-off.** Filtering on structured metadata scans every line of the selected streams instead of using the index. Over long ranges, queries without a narrowing `host_name` selector get slower. The raised limits also let a single record use more memory.

### 5. Onboarding through managed settings

**Problem.** Telemetry must be on for every user of a VM without touching anyone's shell profile, and it must survive non-interactive `claude -p` runs. A repo-level `.claude/settings.json` can't enable exporters.

**Decision.** A Claude Code managed-settings drop-in. nexus writes one per persona and mounts it into the persona's container (README step 2). By hand, a block run as root (REFERENCE.md) installs two files:
- the CA certificate, at `/etc/otel/otel-ca.crt`;
- a Claude Code managed-settings drop-in, `/etc/claude-code/managed-settings.d/50-otel.json`. It holds the exporter settings, the endpoint, the bearer token, `NODE_EXTRA_CA_CERTS` and `OTEL_RESOURCE_ATTRIBUTES`.

Managed settings apply to every user and need no shell environment. Their values are literal (no shell expansion), so the shell fills in each VM's `host.name` when the file is written.

Two client behaviours shaped the design:
- Claude Code does not set `host.name`, so it is **required** in `OTEL_RESOURCE_ATTRIBUTES`. Without it, VMs can't be told apart.
- Claude Code's HTTP exporter ignores `OTEL_EXPORTER_OTLP_CERTIFICATE`, so the CA is trusted through `NODE_EXTRA_CA_CERTS`.

REFERENCE.md records the other client quirks, with the error text where there is one.

**Trade-off.**
- By hand, managed-settings onboarding needs root on each VM; without root, each user must set the same variables in their own shell (REFERENCE.md). nexus needs only Docker access.
- With the hand-written file, every user's Claude Code must read it, so every local user can read the bearer token (nexus keeps its copy readable by its own user only). All VMs share that one token.
- Managed settings take effect only for new sessions. Running sessions must be restarted after onboarding and after a token rotation, and until they are, a rotated token means 401 errors and dropped data.

### 6. A second agent, labelled on the server: Grok Build

**Problem.** Grok Build sends metrics and events, but it ignores `OTEL_RESOURCE_ATTRIBUTES`. Where this stack was built, Grok Build runs under nexus *personas* (named agent profiles), and its data arrived with no VM and no persona. nexus's `--config` command has a telemetry action that sets Grok Build's exporter environment, including two request headers: `X-Nexus-Host` (the VM) and `X-Nexus-Persona`.

**Decision.** The labels are added on the server, from request metadata:
- The OTLP receivers keep request headers (`include_metadata: true`).
- `resource/nexus` copies `X-Nexus-Host` into `host.name` on the resource. That becomes the `host_name` label in Prometheus and an index label in Loki.
- `attributes/nexus` copies `X-Nexus-Persona` into `persona` on every data point and log record. That becomes a Prometheus label and a Loki structured-metadata field.
- Both processors use `action: insert`, which writes a value only where it is missing. Claude Code's own values stand, and data without the headers passes through unchanged.

Grok Build itself needed no change. A Grok Build started without nexus gets the same labels if the headers are set by hand.

**Trade-off.**
- The headers are asserted by the client. The labels are only as trustworthy as the shared token: any token holder can claim any VM name for data that lacks its own `host.name`.
- The token sits in the per-signal (metrics and logs) header variables instead of `OTEL_EXPORTER_OTLP_HEADERS`, so other tools in the same shell, such as docker compose or anything that exports only traces, don't inherit it. The protection is partial: a tool in that shell that reads the metrics or logs header variable still sends the token.

### 7. Same questions, different data model: the Grok Build dashboard

**Problem.** The Grok Build dashboard answers the same questions as the Claude Code one: cost, tokens, sessions, tools and latency, by VM, persona and user. But Grok Build reports its data differently, and copying the Claude Code queries would give wrong numbers:
- **Token types overlap.** Claude Code's token types are disjoint. In Grok Build, `input` includes `cache_read`, and `output` includes `reasoning`, so summing every type would count cache reads and reasoning twice. This was checked against the cost Grok Build reports. A cost model that treats cached tokens as part of `input`, and reasoning as part of `output`, reproduced the reported cost of each of the 16 API calls checked exactly. Treating the types as separate would need a negative price for cached tokens.
- **No usable session counter.** `grok_code_session_count_total` carries only `session_id` (no user or model), and not every session sends it.
- **No event names.** Grok Build's log records have an empty body and no `event_name`, so a model API call can't be selected by name the way Claude Code's `api_request` can.

**Decision.**
- Total tokens are `input + output`, and the cache hit ratio is `cache_read / input`. The **Tokens by Type** stat and the stacked **Token Usage by Type** chart split the total into four disjoint parts: uncached input (input − cache read), cache read, output excluding reasoning, and reasoning.
- Sessions are counted as distinct `session_id` values with token usage in the period. Every variable (VM, persona, user, model) is filled from `grok_code_token_usage_total`, which every session that used tokens reports: always with `model`, and with VM, persona and user when the data carries them. Data without them is shown as `(none)`, and a **Sessions without persona** stat counts the sessions whose data arrived without the nexus headers.
- Events are recognised by the fields only one kind of event has: `stop_reason` for model API calls, `prompt_length` for prompts, `tool_call_count` with `duration_ms` for turn ends, and `tool_name` with `duration_ms` for tool results. Each event panel's description names its field.
- Every dashboard carries an **Agent telemetry** menu that links to the others.

**Trade-off.**
- The event heuristics depend on Grok Build's current attribute sets. A new event kind with the same fields would be counted with the wrong kind.
- A session that hasn't used tokens yet doesn't count.
- Grok Build has two turn-latency timers. One, `ttfm`, is undocumented, so the **Turn latency** panel plots it under that name without saying what it measures.

### 8. Work logs and flow timelines: tables across three backends

**Problem.** The main dashboards answer "how much": cost, tokens, sessions. Reviewing an agent's work needs "what": which session ran which prompts, which tools and commands each prompt used, which workflow runs it started, and when each persona was busy. That detail is spread over three backends: cost, tokens, commits and edits in Prometheus; prompts, model calls and tool calls as Loki events; the program behind each Bash call only as a Tempo span attribute. Grafana's usual browser-side join of query results falls apart when one input is empty. A per-call table built from a Loki metric query exceeds Loki's 1000-series limit after a few hundred tool calls, and Tempo's default 24-hour limit on metrics queries rejects a week-long view.

**Decision.**
- A **work log** per agent: tables from **Sessions** down to individual **Tool calls**. A click on a session sets the Session filter and narrows the time range to that session, and a click on a prompt sets the Prompt filter.
- Tables that combine backends are joined on the Grafana server by a SQL expression over hidden Prometheus and Loki queries. Each query ends in a placeholder row, so an empty input still has the columns the SQL needs; the SQL drops the placeholder.
- Per-call tables come from Loki log queries, turned into columns in the browser, so the series limit doesn't apply. Grok Build's tool calls are the exception: two log queries, decisions and results, joined by SQL on the server.
- Shell commands come from TraceQL metrics over Claude Code's tool spans, and `tempo.yaml` raises the metrics range limit to Tempo's 14-day retention.
- With the agents' tool-detail setting on, the per-call tables also show the command, file path and tool input (Claude Code) or the file path and a parameter preview (Grok Build), and Shell commands shows the full command line. Most of these columns appear only once the data carries their field; Grok Build's Tool calls always shows them, empty until then.
- A **flow timeline** per agent: state-timeline lanes (prompts, model calls, each tool, sessions, workflow runs), one repeated row per persona.

**Trade-off.**
- Event tables show the newest 5000 rows, and summary tables fail with a series-limit error above about 1000 sessions, so long ranges need narrowing.
- Columns from different backends can disagree: Prometheus counts advisor-model tokens that Claude Code's per-request events don't carry.
- Data without a persona gets no per-persona timeline row and appears only as `(none)` in the overview. Only nexus or a hand-set resource attribute (or header, for Grok Build) provides one.
- Commands and file paths appear only with the agents' tool-detail opt-ins on. Those store sensitive data, so they are off by default, and the collector masks secret shapes in them, best effort ([Also in the stack](#also-in-the-stack)). With them on, Shell commands has one row per distinct command line, and a full Claude Code Tool calls table can be about 30 MB per refresh.

### 9. Conversations: a transcript from telemetry, with diffs built in SQL

**Problem.** The work log lists what each session did, but reviewing a session means reading it in order: each prompt, the reply, every step, what each tool returned and the file changes it made. Tools that show this read the agents' local transcript files. This stack only receives OpenTelemetry, and the agents send the text and tool output only with opt-in settings: Claude Code puts tool output on trace spans as a `tool.output` event (an Edit's patch as JSON hunks), and Grok Build puts tool input and output on its log events. Grafana has no diff or chat panel, and installing a community plugin would let any Grafana editor run JavaScript.

**Decision.**
- A **conversations** dashboard per agent, core panels only: a list of conversations, then each talk's prompt, reply and a collapsible list of its steps, flow lanes (and, for Claude Code, the talk's trace), every step with an inspector for its fields and output, and the conversation's file changes.
- Claude Code's diffs are rebuilt by a Grafana SQL expression: it reads Tempo's raw search response, splits each patch into hunks, unescapes the lines and joins them under `@@` headers in a diff code block. A cut patch is closed after its last complete line and marked. Grok Build's changes are rebuilt from the edit tool's input in LogQL, since it reports no patch.
- Agent text only appears inside code blocks, and Grafana's HTML sanitizer stays on.
- `tempo.yaml` raises Tempo's limits to 128 KB per attribute and 20 MB per trace, so 60 KB tool outputs and long prompts fit. The collector keeps one copy of Claude Code's prompt, which it otherwise sends twice with no size cap.

**Trade-off.**
- Text, commands and file contents appear only with the agents' opt-in settings, which store sensitive data; masking is best effort.
- Generated session titles, injected context and reasoning exist only in local transcripts, so they are not shown. Grok Build doesn't send a subagent's parent, so its subagents appear as separate conversations.
- The SQL works within Grafana 13.2.3's SQL-expression limits (10,000 characters, a 1024-byte `GROUP_CONCAT`, a server error on any NULL output column), so the queries carry placeholder rows and recursive joins that are harder to change.

## Also in the stack

- **Traces.** Tempo 3.1.0 runs as a single process on local disk, with no Kafka and no object store. Its metrics generator derives span metrics, which give RED metrics (rate, errors, duration) per span name, and a service graph, and remote-writes both to Prometheus. That powers the service map and the Claude Code dashboard's interaction-duration heatmap. `hostname: tempo` is pinned, so recreating the container doesn't start a new set of span-metric series. The cost is no replication: one process does ingestion, querying, compaction and retention.
- **Links between signals.** An engineer who sees a cost spike needs to get from the metric to the prompt that caused it, so the provisioned datasources link the three signals:
  - *Exemplars* are sample points that carry a trace ID. The Prometheus datasource turns an exemplar's trace ID into a Tempo link, whether the ID is in the `trace_id` label (SDK exemplars) or in `traceID` (Tempo's generated metrics). The links appear wherever exemplars are queried, such as Explore; the provisioned panels don't turn exemplars on.
  - Log lines with a `trace_id` link to the trace.
  - A span links to its logs (±5 minutes, filtered by trace ID) and to its span metrics (request rate, error rate and p95 latency).
  - The service map is built from the service-graph metrics, and the node graph draws each trace from its own spans.
- **Dashboards as code.**
  - All eight dashboards are JSON files in the repo, provisioned with `allowUiUpdates: false`. The Claude Code dashboard is Grafana's home page. A file change takes effect within a minute. The cost is that nothing can be edited in the UI: changes need shell access to the server, and "Save as copy" copies drift from the provisioned version.
  - The Claude Code dashboard's filters apply wherever the data has the matching label. Two exceptions: the interaction-duration heatmap, whose span metrics carry no VM, user or environment labels, and the API-error panels, which ignore the model filter.
  - Testing the Claude Code dashboard found three stack problems (commit 01ac3b1). One was the lookback gap after idle periods. The other two were Tempo's 7-day cap on search ranges and Loki's 30-day cap on query length. Both caps are now 0 (no cap), so retention is the only limit on a query's range. The cost is that a single query from any Grafana user can scan all 30 days of logs or 14 days of traces, which is slow and can push Loki or Tempo toward its memory cap.
- **Hardening.**
  - Every long-running service shares one YAML anchor: a read-only root filesystem, all Linux capabilities dropped, and `no-new-privileges`.
  - Each service has a memory cap (collector, Prometheus, Loki and Grafana 1 GiB, Tempo 1.5 GiB) and a `GOMEMLIMIT` below it. `GOMEMLIMIT` is the Go runtime's soft memory ceiling. It is about 88 % of the cap for most services. The collector's is lower, 640 MiB, about 80 % of its `memory_limiter` hard limit (itself 80 % of the 1 GiB cap). The limiter starts refusing data at its soft limit, 60 % of the cap.
  - The collector and Loki images are *distroless*: they have no shell and no `wget`. The `init` container copies a static busybox into a `probe` volume, which those images mount read-only to run their healthchecks.
  - Grafana is HTTPS only, with secure cookies. Sign-up, public dashboards, external snapshots, usage reporting and update checks are off. The Drilldown and Advisor apps are pinned to exact versions with auto-update off.
  - Every pulled image is pinned to an exact version tag. The cost is that every upgrade is a manual, per-image procedure, and major versions can break configs: Tempo 3 rejects Tempo 2's `compactor:` block outright.
- **Secret masking.** With the agents' detail settings on, commands, file paths, tool input and prompts reach Loki and Tempo, where every Grafana user can read them, and they can hold credentials. Grok Build scrubs secret shapes itself before sending; Claude Code isn't known to. A collector `transform` processor, `transform/redact_secrets`, runs right after the memory limiter in the logs and traces pipelines and replaces common secret shapes with `****` in string attributes and log bodies: private key blocks, auth and cookie headers, URL and `curl -u` passwords, the values of keys and flags named like a password, secret or token, and known token prefixes. It keeps the part that says what was masked (`Bearer ****`, `GITHUB_TOKEN=****`, `ghp_****`), so a masked command still reads. Values often sit inside JSON strings, so escaped quotes and newlines count as delimiters. Masking on the server covers every agent at once and needs no change on the VMs. The cost: it is best effort (an unknown format, a secret split across values, a token cut short by the agent, a secret in a file path or a value nested in a map gets through), a few harmless values are masked too, and it never rewrites data already stored.
- **Secret scan in CI.** The repo is public, so every push and pull request runs `tests/secrets.sh`: gitleaks, pinned by digest, in a container, over every commit, every commit and tag message, and the files in the checkout. What git ignores (`.env`, `otel-ca.crt`) never goes in, and a finding is printed as its rule, file, line, commit and fingerprint, never the secret. Before scanning, it checks that its rules catch a fake token it plants, so a broken config fails loudly instead of passing. The cost is that CI scans after the push: anything it finds is already on GitHub, so the runbook says to run the same script before pushing.
- **Docs.** `README.md` covers setup in three steps, each code block labelled with where it runs. `REFERENCE.md` covers how the stack works, including Grok Build setup. `runbook.md` covers operations, with troubleshooting by symptom. `EXAMPLES.md` has a smoke test, SDK setup for other apps, and queries. A review by a reader new to the docs (commit 5dc2420) made four changes:
  - The restore procedure is split, so a wrong backup path stops before `docker compose down -v`.
  - The command that shows the token for a new VM prints only the token, not the rest of `.env`.
  - The agent-side command for rotating the token is written out.
  - The Grafana provisioning note in the "Apply a change" table is corrected.

- The dashboard commit (01ac3b1) says the Claude Code dashboard was tested against the stack. That testing found the lookback gap and the query-range caps.
- `REFERENCE.md` says the Claude Code managed-settings setup was verified with Claude Code 2.1.302.
- The Grok Build labelling was tested on a local copy of the stack with real Grok Build 1.0.62 and Claude Code 2.1.303 (59f9ac9). Grok Build's series carried `host_name` and `persona`, its events could be found by persona in Loki, and Claude Code's data was unchanged.
- The commit that added the Grok Build dashboard says every one of its queries was run against live data and through Grafana's query API, with the filters set to All, to single values and to values that match nothing. The usage table's columns summed to the stat panels' totals, and every token part was non-negative (cache_read ≤ input, reasoning ≤ output). It also says the token accounting was checked against the cost Grok Build reports.
- `EXAMPLES.md` says the generic SDK setup was checked with the Python and Node.js SDKs.
- The work logs and flow timelines were checked two ways against live data. First, every query ran through Grafana's query API, with the filters set to All, to one session, to one prompt and to a VM with no data. Second, every panel was rendered in a headless browser, and the session, prompt and trace links were followed. The browser pass found three problems that the query API passed: a pie legend in the Grok Build dashboard that showed `Value #A` instead of stop reasons, a timeline overview drawn in invisible colours, and the Claude Code dashboard's **Recent interactions** panel, which was empty on data without an environment attribute.
- The secret masking and the tool-detail columns were tested before they were committed, with scripts that are not in the repository. Collector 0.162.0 ran offline on synthetic logs and traces: 144 values that must be masked, 85 look-alikes that must stay (`docker run -u 1000:1000`, `max_tokens=100`, `--password-stdin`), 6 known false positives, string bodies, and non-string attributes that must pass unchanged; all 914 checks passed, including that every masked JSON value still parses. Running the rules over about 12,700 lines of docs and about 5,100 real Claude Code tool inputs found false positives the test cases had missed, such as `grep '^PASSWORD=' .env`, and they were fixed. Then a separate copy of the stack, on its own network and loopback ports, received realistic Claude Code and Grok Build records carrying fake secrets. Loki and Tempo stored them masked, apart from two known limits (a token cut short by Claude Code, a value nested in a map), and both work logs showed the new columns with the masked values. That pass found one dashboard bug: Shell commands showed `0` instead of a blank for spans without a full command. A later review found gaps the tests had missed. The worst two: a password in a command's own JSON, which `tool_parameters` escapes a second time, was not masked, and masking a single-quoted value could break the JSON around it, which blanked the Command and File columns. It also found secrets the rules didn't know (`DB_PASS=`, `aws configure set`, `Authorization: OAuth`) and JavaScript masked for no reason (`credentials: 'include'`). All were fixed and added to the offline tests (the counts above include them), and the sweeps over docs and tool inputs were run again; the stack copy was not run again.
- The core claim of decision 1, that dashboard totals match a known number of sessions, has no recorded test. The smoke test only checks that one delta sample arrives in Prometheus as a cumulative value of 1.

The repository reports no usage volumes, cost figures or performance benchmarks.

## Limitations and trade-offs

The decisions above state their own trade-offs. These are the limits of the stack as a whole:

- **Exactly one collector.** Counter conversion state lives in its memory ([decision 1](#1-counting-correctly-with-delta-counters-and-short-lived-series)), and agents don't spool, so data sent while it is down is lost.
- **Single node, no replication.** Prometheus, Loki and Tempo each run as one instance on local disk. Backups are cold: the backends are stopped and their volumes archived.
- **No alerting.** Prometheus has no rule files, there is no Alertmanager, and Grafana provisions no alert rules. A growing queue, dropped data or an expiring certificate is seen only by someone who opens the Claude Code dashboard's **Collector health** row or runs the runbook's health check.
- **Retention differs per backend.** Prometheus keeps 15 days or 3 GB, whichever comes first. Loki keeps 30 days and Tempo 14 days, with no size cap. On a dashboard range longer than about two weeks, different panels, even within one row, cover different periods without warning. Shortening retention is easy to get wrong: Tempo's retention is set twice, and the per-tenant value wins. Prometheus's 3 GB cap counts its write-ahead log, which retention never deletes.
- **Every Grafana user is effectively a stack admin.** Through the datasource proxy, anyone who can log in can reach the Loki and Tempo HTTP APIs, including Loki's ingester shutdown endpoint.
- **Secret masking is best effort.** With the agents' detail settings on, a secret in a format the collector doesn't recognise is stored as sent, and every Grafana user can read it.
- **One shared bearer token.** Every local user on every Claude Code VM can read it. Rotating it means updating every agent, and data from agents that haven't been updated yet is rejected with 401.
- **Docker bypasses the host firewall.** Published ports bypass host `INPUT` rules such as ufw. Limiting access needs a `DOCKER-USER` iptables rule, which the docs provide as an optional step.
- **Cost is the agents' own estimate.** The dashboards show the cost each client reports, not billing data.
- **Client-side gaps** remain outside the server's control: Claude Code sometimes loses the root span in `-p` mode, and Grok Build fails exports silently.

## Lessons learned

1. **Delta counters over per-session series need deliberate handling.** Plain `increase()` gives plausible but wrong totals. Correct totals took a collector processor, two experimental Prometheus features, a tuned lookback window and a fixed query pattern. The repository records no check of the result against a known session count ([How it was verified](#how-it-was-verified)), so run one before relying on the totals.
2. **Don't assume two agents mean the same thing by the same metric.** "Input tokens" excludes cached tokens in one client and includes them in the other. A cross-check against the client's own per-call cost settled it; copying the Claude Code queries would have double counted.
3. **Tune defaults for a replayed backlog, not only for steady state.** Two Tempo defaults quietly drop data that arrives late after an outage. A disk queue is only useful if the backends accept what it replays.
4. **Each client has its own TLS and configuration quirks.** Claude Code needs `NODE_EXTRA_CA_CERTS`, Grok Build needs `OTEL_EXPORTER_OTLP_CERTIFICATE`, and Claude Code's gRPC exporter refuses an IP address as the TLS server name. These came out of testing with the real clients. The docs record each one, with the exact error text where there is one; for Grok Build, which fails silently, they give a debug-log check instead.
5. **Label on the server when the client can't.** Header-based, insert-only enrichment made a second agent's data attributable by VM and persona without changing that agent's code, and without touching the first agent's data.
6. **Dashboards find stack problems, and browsers find dashboard problems.** Long time ranges hit Tempo's and Loki's default range caps, and idle gaps exposed the lookback gap. All three were found while testing the dashboard. Later, rendering the dashboards in a browser found three panels that the query API had passed but that showed wrong labels, invisible colours or nothing at all ([How it was verified](#how-it-was-verified)).
7. **Know what each workaround buys.** The `certs` container and `init`'s chown of the queue volume are the price of a Docker-only host. The busybox probe volume is the price of using distroless images without building custom ones. The per-UID key copies come from running each consumer as its own non-root user. One visible cost: services depend on the one-shot containers having completed, so `docker compose start` fails once those containers are pruned, and the docs use `docker compose up -d` throughout.
8. **Test a masking rule on real input, not only on secrets.** Synthetic secrets show what a rule catches; only real commands show what it breaks. Test every depth of escaping the data has, too: a command's own JSON inside `tool_parameters` is escaped twice, and the first rules missed it. Running the rules over real docs and tool inputs found false positives that no test case had, such as `sed 's/^PASSWORD=//p'`. Shape rules also stay best effort: a token that the client cut short no longer looks like a token.
